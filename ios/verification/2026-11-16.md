# Native iOS app verification — 16 November 2026

## Result

Built the native SwiftUI Leafy app and exercised it in the **iPhone 17 Pro simulator, iOS 26.1**. It uses the existing API bridge without firmware or PCB changes. The app remains open against a local fake-car fixture for review. No actual vehicle commands, private credentials, GitHub push, physical iPhone install or App Store/TestFlight publication were involved.

The app displays BMS battery percentage and age, protected supply voltage, connection status and explicit heater request results. It saves the server/app token in Keychain, confirms Heat On, persists command intent before delivery and never automatically retries a heater command.

## Automated results

- Seven Swift model tests passed (zero failures), using the production model and client types with an injectable transport/storage boundary. These first failed against incomplete behavior, then passed after implementation. Coverage: connection policy, token persistence, read-only connect, offline clearing/disabled controls, persistence before send, restart without replay, unknown-result lookup and Off, storage failure, sample age, background clearing and forgetting settings.
- Existing **23 Node server tests passed**, including the local HTTP integration tests.
- `xcodebuild build` and `build-for-testing` succeeded for the simulator. Both unit and UI test targets compile. The only final build notices were Xcode's skipped App Intents metadata extraction; no App Intents are implemented.
- Xcode's automated simulator test execution could not start: `DTServiceHubClient failed to bless service hub` / `localDeviceConnectionWithError`. It occurred on both installed iOS 26.3 and 26.1 runtimes with Xcode 26.3 on macOS 27.2.1. No XCUITest execution pass is claimed. No system security setting was changed to bypass it.
- SwiftPM's reused build cache also reported `unknown build description`. The repeatable [logic-test script](../scripts/test-logic.sh) uses an isolated temporary cache; the final seven tests passed using it.

## Interactive checks on the running simulator

These checks operated the real SwiftUI app through its native UI. The app used URLSession over loopback HTTP to the real Node API bridge, which used a separate loopback fake-board server. No in-app fake data path or real-car credentials were used.

| Check | Observed result |
| --- | --- |
| Fresh install / no connection | Setup required; no heater controls shown; Connect disabled until fields are filled. |
| Invalid address / incorrect token | Validation error / “App token not accepted”; no commands sent. |
| Successful connection | BMS 92.5%, protected supply 13.70 V, age displayed; setup saved in Keychain. These are fixture values. |
| Heat On cancellation | Confirmation shown; cancelling left fake-board command count at zero. |
| Heat On / Heat Off | Exactly one `/api/on` then one `/api/off`; accepted-request messages, no claim of actual heater state. |
| Stale battery | “Last known · 4m ago,” with percentage retained as historical data. |
| Board status failure | Percentage and voltage cleared to `—`; both heater controls disabled; connection error shown. |
| Missing SOC | “Waiting for the car to send a reading”; percentage `—`, voltage still available. |
| Connection recovery | Readings and controls returned; no new command. |
| Lost command response | One additional On reached the fake board; app displayed uncertainty and disabled new On while leaving explicit Off available. |
| Check request result | Lookup did not increase the command count. |
| App terminate/relaunch | Connection/token and uncertain result restored; On remained blocked; command count unchanged. |
| Explicit Off after uncertainty | One Off request accepted; normal control availability returned. |
| Forget/reconnect | Setup returned with empty fields; reconnect succeeded and restored the latest same-server command result. |
| Commissioning lock | Both heater controls disabled with an explicit lock explanation. |

Final fake-board delivery log: `on, off, on, off`, with the third call intentionally losing its response. See [fixture result](simulator-fixture-results.json). Status polls, cancellation, reconnect, lookup and relaunch added no commands. The fixture was restored to fresh data with heat request false.

Screenshots: [setup](setup.png), [dashboard](dashboard.png). They contain only test values and the public, non-secret simulator configuration.

## Remaining acceptance

- Sign/install on the owner's iPhone; test Local Network permission, reachable home-server setup, Keychain behavior on the physical device and foreground/background recovery.
- Perform supervised real-vehicle On/Off through the app, verifying the car itself. The prior website tests do not constitute app/bridge vehicle acceptance.
- Retest XCUITest execution when the host/Xcode test-service issue is resolved; the interactive checks above are not an automated UI pass.
- Validate smaller-device/iPad layouts, larger accessibility text and dark mode before a broader release. The current simulator review used the normal light appearance on iPhone 17 Pro.
- Dashboard SOC is not exposed by the current JSON API. The app labels its reading BMS; it does not invent the dashboard percentage or countdown from unavailable API fields.
- A permanent home server, remote access, App Store distribution and heater-state feedback are outside this change. Existing vehicle power/timer/long-term checks still apply.
